# 📋 工作流程规范 (Workflow Specification)

## 1. 角色定义

| 角色 | 职责 |
|------|------|
| **架构师 (Architect / Planner)** | 负责需求分析、架构设计、任务拆分、技术选型，以【任务包指令】形式下达任务 |
| **执行 Agent (Execution Agent)** | 负责按指令编码实现、运行测试、提交代码，并以【执行报告】形式汇报结果 |

## 2. 工作流概览

```
架构师 ──[任务包指令]──▶ 执行 Agent ──[编码+测试]──▶ [执行报告] ──▶ 架构师审核
                                                         │
                                                    ┌────┴────┐
                                                    ▼         ▼
                                                 通过      需修改/阻塞
                                                    │         │
                                                    ▼         ▼
                                                 归档    架构师决策
```

## 3. 任务包指令格式 (Task Package)

架构师下发的每个任务必须严格遵循此格式：

```
# 📥 [TASK_PACKAGE] 任务指令包
**任务编号:** #T{自增序号}
**所属阶段:** [如：MVP-前端UI搭建 / 数据库设计]
**优先级:** [P0-Critical / P1-High / P2-Medium / P3-Low]

## 1. 任务背景与目标 (Context & Goal)
- 简述为什么做这个任务，期望达成什么结果。

## 2. 核心技术栈与规范 (Tech Stack & Rules)
- 指定语言、框架、命名规范。

## 3. 具体执行步骤 (Action Items)
- [ ] 步骤 1：创建文件 `xxx.xx`
- [ ] 步骤 2：实现函数 `yyy()`，输入输出要求...
- [ ] 步骤 3：编写对应的单元测试 / 运行测试。

## 4. 交付物要求 (Expected Deliverables)
- 需修改/创建的具体文件路径列表。
- 需提供的终端运行截图或日志输出。

## 5. 验收标准 (Acceptance Criteria)
- [ ] 所有测试通过
- [ ] Lint / Type Check 无报错
- [ ] 功能满足描述需求
```

## 4. 执行报告格式 (Execution Report)

执行 Agent 完成任务后必须严格遵循此格式回报：

```
# 📤 [EXECUTION_REPORT] 执行结果报告
**回应任务编号:** #T{任务编号}

## 1. 执行状态 (Status)
- [x] ✅ 成功完成所有步骤
- [ ] ⚠️ 部分完成 (存在未决问题)
- [ ] ❌ 失败 (遇到严重阻塞)

## 2. 工作详情 (Work Details)
- **新增/修改的文件:** (列出路径及主要改动)
- **运行命令与结果:** (如 `ruff check` 的输出)

## 3. 遇到的问题与报错 (Issues & Errors)
- *如果没有则填"无"。*
- *如果有，请提供完整的 Error Log 和初步分析。*

## 4. 需要架构师决策的事项 (Request for Decision)
- *例如："需要依赖的第三方库 A 和 B 选哪个？"*
- *或"当前架构设计在实现某功能时存在冲突，请求修改架构方案。"*
```

### 4.1 回报前置条件 (MANDATORY PREREQUISITES)

在输出执行报告之前，Agent **必须**完成以下操作：

1. ✅ `ruff check .` — 无报错
2. ✅ `mypy .` — 类型检查通过（如项目已配置）
3. ✅ `git add -A && git commit -m "[#T{编号}] {type}: {描述}"` — 已提交
4. ✅ 检查工作区干净: `git status` 无未暂存变更

## 5. 任务状态与流转

```
                    ┌──────────┐
                    │  PENDING │  ← 架构师下达任务
                    └────┬─────┘
                         │
                    ┌────▼──────┐
                    │ IN_PROGRESS│  ← Agent 开始执行
                    └────┬──────┘
                         │
              ┌──────────┼──────────┐
              ▼          ▼          ▼
         ┌────────┐ ┌────────┐ ┌────────┐
         │ PASSED │ │BLOCKED │ │ FAILED │
         └────────┘ └───┬────┘ └───┬────┘
                         │          │
                    ┌────▼────┐     │
                    │ 决策后  │     │
                    │ 重新执行 │     │
                    └─────────┘     │
                               ┌────▼────┐
                               │ 架构师   │
                               │ 重新规划 │
                               └─────────┘
```

## 6. 沟通规范

- **任务包指令** 由架构师在项目 Issue 或项目管理工具中发布，一条 Issue = 一个任务包。
- **执行报告** 由 Agent 直接回复在原 Issue 下。
- 遇到阻塞问题时，Agent 必须在执行报告中"需要架构师决策的事项"一栏清晰描述阻塞点和可能的解决方案。
- Agent **不得**自行进行架构级别的决策（如引入新的第三方库、修改数据库 schema 等），必须通过 `Request for Decision` 机制提请架构师审批。

## 7. 代码提交规范 (MANDATORY)

- **每个任务包完成后，Agent 必须在回报前执行 `git commit`。**
- Commit message 格式：`[#T{编号}] {type}: {简短描述}`
- Type: `feat` / `fix` / `refactor` / `test` / `docs` / `chore`
- 示例：`[#T001] feat: 搭建 FastAPI 项目骨架`
- **不要**在未经架构师批准的情况下 push 到远程仓库。

## 8. 测试要求

- 每个任务包涉及的功能代码**必须**有对应的单元测试。
- 测试覆盖率目标：≥ 80%（核心业务逻辑）。
- 提交前必须运行以下检查（如项目已配置）：
  - `ruff check` (Lint)
  - `mypy` (Type Check)
  - `pytest` (Unit Test)
